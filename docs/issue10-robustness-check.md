## 保存重试与重复分享

- K02 / F01 测同一次保存。用相同的入口、`operationId` 和参数重发 E01。两次回执逐字段一致，库中只有一条记录、一份来源和一个整理任务。
- G09 测同一经历再次分享。先录入两条工作日加班经历 E01、E02，再用新的 `operationId` 分享 D01。来源可增加一条，独立加班经历和“优先省事”的支持次数都保持 2。E03 按周末例外核对，R01 按室友转述核对。[晚餐样例](testing/issue10/fixtures.json) · [计数与条件](testing/issue10/expected.json)

## 调度与仓储联调

每项从空测试库开始。调度场景先开启自动整理并保存 E01，用回执里的 `jobId` 核对操作前后的任务修订、状态、阶段和检查点。[任务接口](core-api-contract.md) · [共享契约测试](../android/app/src/sharedTest/java/com/pebblepile/android/service/CoreApiContractSuite.kt)

| 操作 | 怎样验收 |
| --- | --- |
| 提交一个阶段后暂停。用暂停前的租约提交下一阶段，再继续任务。 | 暂停原因为 `user_paused`，检查点保持原值。继续后从该检查点接着跑，该阶段只提交一份结果。 |
| 在工作进程持有租约时取消任务，再让它交回结果。 | 任务保持 `cancelled`，原话仍可回查，阶段结果和后继任务数保持原值。 |
| 按 F02 中止进程并重开，让新执行者接手同一阶段。在调度测试里再提交旧执行者的结果。 | 按原 `jobId` 查到最近一次已提交的检查点。只有当前租约能推进任务，同一阶段只提交一次，标签与证据计数和正常跑完一遍相同。 |
| 让算法阶段首次返回可重试错误，下一次返回正常结果。 | 任务保留失败原因和已提交的检查点，重试成功后只发布一次结果。用 C01 纠正后再交旧结果，按 F04 核对 `STALE_INPUT` 和当前修订。 |
| 在 SQLite 测试库占用写事务，再从另一连接保存 E01，随后释放锁。 | 写入成功时按 K01 核对完整记录、来源、任务和回执。若返回可重试的写入错误，先核对四项都保持原值，再用原请求重试，最终各有一份。 |
