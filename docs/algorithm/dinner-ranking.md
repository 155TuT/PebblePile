# 晚餐推荐怎样使用记录和偏好

0.1.0 的晚餐建议来自随包的六道菜。用户提问时，应用从原话和当前事项中读出星期、加班情况、预算与可用时间，先筛掉超出预算或时间的菜，再用符合本次条件的偏好和经历排序。默认引擎使用本地词表和规则，整条计算链在设备上运行。[饮食场景实现](../../lib/algorithm/)

## 从原话到建议

| 步骤 | 输入与处理 | 结果 |
| --- | --- | --- |
| 抽取 `extract` | 在指定来源版本中识别经历者、饮食事实和语义标签。 | 加班、金额、菜名和用时等原文片段附来源 ID、版本和 Unicode 码点区间 `[start, end)`，可用 `CodePointSpan.quoteIn(text)` 取回引文。星期和周末例外等条件由抽取规则判定。 |
| 更新 `update` | 取同一来源的最新版本，合并重复经历，再按记录排除用户修订的标签。 | 两次独立的本人工作日加班经历都支持“省事”时，形成推断偏好。单次支持保留为弱候选。周末愿意慢慢做饭的经历单独保留，本人明确设置的条件优先生效。 |
| 排序 `rank` | 从菜单中筛出符合预算与准备时间的菜，在命中的条件下比较偏好和经历。 | 返回有序候选、筛除项、采用及未命中的偏好，以及各候选的理由和证据。 |

重复分享保留各自的来源版本，计数按经历归并。Android 整理任务会去除原文首尾空白、统一换行，再按文本摘要归并。引擎接口还支持传入 `eventId`，调用方可以用同一编号标明措辞不同的两份材料来自同一次经历。

`DietTaskPipeline` 从 Room 读取允许整理的来源版本，在写事务外计算，按抽取、更新、提问条件和排序保存四个检查点。`RANK` 检查点保存本次条件、排序结果、偏好设置修订及算法清单。普通记录完成整理。晚餐提问缺少必要条件、纠正语句需要确认，或筛选后的菜单为空时，任务转为待核对。

发布建议时，`RoomTaskStore.finishIfCurrent` 在同一事务内核对租约、输入与偏好修订、整理授权和原文区间，再把候选、依据和决定编号写回记录。用户明确设置的条件在所属记录中唯一匹配到原话时，附 `explicit_rule` 引文。详情用 `getRecordDetail` 读取建议，反馈用 `recordOutcome` 指明当时的决定编号，原建议和实际结果都可回查。[业务接口与仓储契约](../core-api-contract.md)

## 四种提问的回放基线

固定数据集为 `issue10-dinner-v1@0.1.1`，场景包为 `diet-scene-pack-0.1.0`，算法为 `local-rules-0.1.0`，排序基线为 `dinner-ranking-0.1.0`。四次提问的预算都是 20 元，22 元的麻辣烫在评分前筛除。[固定输入](../../test/fixtures/issue10/fixtures.json) · [菜单、候选顺序与原始计时](../../test/fixtures/issue10/algorithm-baseline.json)

| 提问 | 本次依据 | 候选顺序 |
| --- | --- | --- |
| Q01 周四加班 | E01、E02 两次本人的加班经历都支持“省事”。 | 盖饭、热汤面、轻食便当、家常炒菜、番茄鸡蛋面 |
| Q02 周日休息 | 有 40 分钟做饭，E03 记录了周末愿意慢慢做饭的原话。 | 番茄鸡蛋面、家常炒菜、轻食便当、盖饭、热汤面 |
| Q03 周六加班 | 用户通过 C01 把“省事”限定在工作日加班。周六按预算和准备时间比较。 | 轻食便当、盖饭、热汤面、家常炒菜、番茄鸡蛋面 |
| Q01b 周四加班 | 命中 C01，建议同时引用本人的设置及 E01、E02。 | 盖饭、热汤面、轻食便当、家常炒菜、番茄鸡蛋面 |

D01 重复分享 E01，支持次数仍为两次。R01 属于室友，只保留为转述。在算法回放中排除 E01 的“省事”标签后，支持该偏好的经历只剩 E02。O01 记在 Q01 的决定下，当时首选盖饭，实际吃的是热汤面。

## 复跑与计时

在仓库根目录运行以下命令，重新执行基线用例。

```powershell
python scripts/gradle.py :app:testDebugUnitTest --tests "*AlgorithmBaselineTest.rankingIsStableAcrossThreeRuns" --rerun
```

在 `build/native/app/test-results/testDebugUnitTest/` 的 JUnit XML 中搜索 `DINNER_REPLAY`。每行依次为提问编号、轮次、抽取毫秒、更新毫秒、排序毫秒和模型调用次数。每组跑三次，每轮新建默认引擎，先抽取 E01 至 E03，再更新偏好并排序。计时用 `System.nanoTime()`，范围为这三个计算阶段。

基线记录的 12 轮回放在 Windows 11、JDK 17.0.15 上完成，各轮模型调用均为 0。首次运行与后续运行的耗时分别保存在基线文件的 `latencyMillis`。单独调用 `dinnerQuery` 时会复用已抽取的经历，其耗时只覆盖更新和排序。`engine.inferenceCalls` 累计该引擎实际请求模型端口的次数。[回放测试](../../test/unit/algorithm/AlgorithmBaselineTest.kt)
