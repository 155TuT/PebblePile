# 用户研究与同题对照

当一个人再次问“晚饭吃什么”，他要重复说多少背景？看到建议后，他能否找回上次的原话，弄清这次为什么换了一道菜？叠石用同一组晚餐材料比较对话工具、手机便签和 Android 客户端，观察记录、回查和纠正各花多少工夫。

现有材料包括固定原话、访谈提纲和回访方法。访谈计划覆盖 8 人，Beta 重构后邀请其中 4 人用新版本重做原任务。参与人数、耗时和使用感受按实际回访登记。[产品与技术调研](research.md) · [课程冲刺计划](https://github.com/155TuT/2601-fzu-SoftwareEngineering-YuezhongWu/blob/main/homework/team/task8/plan.md)

## 同题使用的晚餐材料

三条经历属于同一个虚构用户。录入时保留原话和发生时间。E01、E02 是两次独立的加班晚餐，E03 用来观察周末愿意花时间做饭的情况。C01 改变以后推荐的适用条件，O01 记在首次 Q01 的建议下。测试使用同一份文字和证据区间。[机器可读样例](testing/issue10/fixtures.json) · [客户端回归步骤](testing/README.md)

| 编号 | 发生时间 | 原文（逐字录入） |

## 怎样比较两款工具

对话组选豆包，记录组选参与者常用的手机便签。也可按设备条件选用灵光或 Notion，登记实际工具和替换原因。

1. 记录设备、Android 版本、应用版本、登录状态、记忆设置和网络状态。在新会话或笔记中录入 E01–E03，记下额外的保存操作。
2. 切换会话或笔记后做 Q01。对话组向工具索要原话，记录组由参与者翻查笔记，给出选择并指出依据。记录他打开了什么、用了多久、补说了哪些背景。
3. 依次做 Q02、C01 和 Q03。对话组在新会话中回答 Q03，记录组先把新条件写进原笔记，再作决定。对照工作日和周末的建议、引用及条件。

| 观察项 | 记录口径 |
| --- | --- |
| 耗时 | 从给出任务到回答或定位原文，包含等待。满 300 秒仍在操作，记为超时。 |
| 操作和补述 | 每次点击、滑动或提交文字计一次操作。每次重复已给出的背景计一次补述，另记主持人的提示。 |
| 依据 | 区分打开对应原文、仅复述大意、未找回。记录实际引用和截图编号。 |
| 纠正 | 记录“优先省事”在周四和周六各自是否生效，以及当时的预算与候选。 |
| 完成情况 | 记录独立完成、提示后完成或未完成，同时写下首次提示或结束的位置。 |

## 访谈与 Beta 回访

招募近一个月至少 3 次遇到同类生活选择的人。计划邀请 4 位以饮食为主、4 位以通勤或学习等其他场景为主的参与者，其中至少 2 位每周使用 AI。每次访谈约 15–20 分钟。记录、匿名引用和保留截图分别取得同意，用 U01–U08 标记参与者。

访谈先让对方演示最近一次真实选择。从哪里翻出旧记录？上次已经说过的背景，这次又解释了哪些？再请他对比最近两次选择的条件和结果，演示建议出错后怎样修改、怎样判断修改生效。分别记录参与者原话和观察，把原任务的条件、目标和卡住的位置记在同一个编号下，例如 `U01-T01`。

Beta 回访沿用这个编号和原任务。每个人用旧方法和叠石各做一次，交替安排先后顺序。先观察独立操作，遇到卡点后再给提示。登记 APK 版本和 SHA-256、两种方法各自的耗时和补述次数、首次提示的位置以及参与者愿意引用的原话。通勤、学习等场景可比较记录、找回与纠正，饮食场景还可比较建议及其依据。

发现可复现的问题时，记录设备与包版本、任务编号、资料库初始状态、操作、预期和实际结果。用修复后的版本重做同一步，连同新包校验值登记复验结果。
